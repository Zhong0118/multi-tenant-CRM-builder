# 字段、列表与业务表生命周期

日期：2026-10-20

交付范围：字段、列表配置与整张业务表停用/恢复已在本地实现。服务器仍为字段生命周期版本 `9136cdc`；本次整表功能未推送或部署。

## 一、配置职责

| 页面 | 管理内容 | 不负责的内容 |
| --- | --- | --- |
| 字段与表单 | 名称、类型、选项、必填、校验、新建/编辑表单顺序、字段启停 | 默认列表列顺序 |
| 列表展示与搜索 | 默认展示列、从左到右顺序、搜索字段、记录默认排序 | 授予读取或编辑权限 |
| 员工权限及成员例外 | 谁可以访问表、哪些记录、哪些字段 | 字段是否继续供整张表使用 |

“不在列表展示”只改变默认排版，详情和表单仍可访问。“员工不可见”限制相应员工读取；管理员不受该员工权限限制。“停用字段”发布后将字段移出所有角色的运行时字段集合。

列表配置是管理员和员工共用的默认值，运行时再按权限裁剪。浏览器中已有的列设置可能覆盖默认值。目前个人列偏好尚未按成员隔离，本轮未调整这一独立问题。

## 二、本轮字段启停行为

入口：公司设置 → 业务表 → 选择业务表 → 字段与表单 → 每行“停用 / 恢复”。

1. 点击操作先展示确认框，说明对所有角色的影响、历史值保留、需要发布。
2. 停用和默认列表/搜索引用清理在同一个后端草稿更新中完成，不分多次请求。
3. 当前记录名称字段必须先在基本设置中换掉，系统字段不能停用；前后端都有检查。
4. 保存后显示“已保存到草稿，发布后生效”。未发布时员工继续使用旧版本。
5. 流程继续引用被停用字段时，沿用发布分析阻止发布并显示问题，不自动删除流程配置。
6. 发布后，表单、详情、列表和搜索不再使用该字段。数据库历史值保留；修改其他字段时也保留这些旧值。
7. 恢复后沿用原字段权限，保存、发布后重新出现于表单/详情。默认列表和搜索需重新勾选，不自动扩大展示范围。
8. 只要字段曾经发布过，其类型和字段键继续锁定，包括停用发布之后。依据发布历史识别，不把当前版本中缺失的字段误判为未发布。
9. 恢复必填字段时，若停用期间新增的记录缺值或无法证明值完整，发布检查仍可能阻止发布。可先把字段改为非必填再发布恢复，不能自动伪造历史值。
10. 多人同时修改时沿用版本冲突校验，不覆盖他人更新。

停用是字段定义的生命周期，不等于删除单选选项，也不等于删除记录。

## 三、整张业务表停用与恢复：本地实现

### 页面与状态

- 复用现有 `DRAFT / ACTIVE / ARCHIVED` 状态，用户界面使用“未发布 / 使用中 / 已停用”。不新建业务数据表，也不复制记录。
- 已发布表的“基本设置 → 停用与恢复”提供“停用业务表”；已停用表显示恢复按钮、停用时间和上次发布版本。管理列表右侧也提供同一确认入口，手机端可用。
- 业务表管理列表提供“全部 / 使用中 / 已停用 / 未发布”筛选。正常业务导航只显示使用中且有权读取的表。
- 未发布的表继续使用“删除草稿”，不把草稿删除与已发布表停用混用。

### 停用确认

确认框列出表名、记录数、上次发布版本、是否存在待发布草稿，以及依赖检查结果；明确这次操作立即生效，不经过字段配置的发布流程。

停用后保留字段、记录、负责人、公海阶段、跟进、附件、关系和发布历史。公司管理员仍能在设置中查看表的管理信息，普通业务页面不再开放。详情直达链接显示“业务表已停用”，不显示“暂无数据”。

修改操作、导入、导出、AI 查询和流程写入均应检查表状态；不能仅靠菜单隐藏。字段草稿在停用期间只读，恢复后再继续编辑，减少状态歧义。

### 依赖检查

- 其他使用中业务表的已发布流程如果需要读写此表，列出来源和动作，先处理依赖再停用。
- 公海成交保护规则如果依赖此表中的订单/合同，也应列出并阻止直接停用，避免意外撤销其他表记录的保护。
- 工作台组件可保留配置并显示“引用的业务表已停用”；不得使整个工作台报错。
- 历史关系和审计保留，跳转到停用表时给出明确说明。

依赖检查在预览时展示，在操作事务内再次检查。并发新增依赖被阻止时展示具体原因；只有 `CONFIG_VERSION_CONFLICT` 才提示重新载入配置。工作台按组件保留 `UNAVAILABLE / OBJECT_ARCHIVED` 状态，其他组件继续显示。

### 自动任务和计时

现有公海回收与站内提醒扫描已存在 `ACTIVE` 过滤，但“停止扫描”和“暂停倒计时”不是一回事。

整表停用期间暂停公海持有时限：增加表级停用时间元数据，恢复时将当时尚未到期的持有期限顺延停用时长，保持剩余时间。停用前已到期的记录仍按已到期处理；永久保护记录不新增回收计时。普通跟进待办的人工截止日期保留，恢复后按原截止时间呈现逾期，不重新计算业务约定日期。

恢复不能一次性补发停用期间每个历史扫描周期的提醒；消息去重继续有效。新建的截止任务、已有未读消息和恢复后链接均需验收。

### 恢复版本与并发

- 恢复直接重新启用停用前的已发布版本，不能调用 publish 把草稿一并发布。
- 原待发布草稿、记录和成员权限保留，恢复不会把员工权限改成全员可见。
- 在同一事务中锁定业务表并校验版本，更新状态和期限，写审计；防止与发布、回收或重复恢复竞争。
- 页面“待发布修改”应准确反映配置差异，不能因为生命周期操作增加了版本号就误报配置变更。
- 历史上已归档却缺少停用时间的表，不猜测顺延时长；恢复前明确展示原期限及已到期数量，由管理员确认处理。

### 整表实施验收清单

1. 公司管理员可操作，员工无操作权限，不能跨公司。
2. 有草稿的表停用后再恢复，运行时仍使用原发布版本，草稿完整保留。
3. 停用时新增、编辑、导入、AI 和流程不能绕过状态；恢复后按原权限访问。
4. 记录数量、历史值、附件、负责人、关系保持一致。
5. 公海期限暂停与恢复可验证；不会恢复即误回收所有记录，不影响永久保护。
6. 有跨表流程或保护依赖时给出具体阻止原因；工作台降级显示而非整页失败。
7. 已停用列表、恢复入口、手机端确认框、刷新与直达链接均可用。
8. 并发停用、恢复、发布、定时任务有事务保护，审计可追溯。

整表本地后端与前端已实现，新增迁移为 `0034` / `0035`；字段启停本身不需要数据库迁移。停用期间字段配置可查看但不可编辑，拖动、选项按钮、列表原生勾选、权限、流程及公共池保存均不能绕过状态。生命周期操作更新当前配置并刷新导航，不调用发布接口。

授权的业务表列表、新建、详情及编辑直达页面在服务端捕获明确的 `OBJECT_ARCHIVED`，显示“业务表已停用”；403/404 延续原有隐私行为。失败预览提供重试，版本变化要求主动重新载入，提交中禁止重复确认或关闭。历史无停用时间的表展示已到期数量并要求勾选保留原期限后才能恢复。

## 四、本地验证记录

- Objects / Record Value Engine：10 个测试文件，374 项通过。
- Web Objects / Templates：12 个测试文件，131 项通过。
- 独立 PostgreSQL（临时容器、独立端口）的发布链路端到端测试通过：发布前保持原字段；停用发布后管理员和员工均不可见；停用期间编辑其他数据仍保留旧值；恢复并发布后旧值重新可读；曾发布字段的类型仍锁定。
- API、Web 类型检查通过。Web 改动文件 ESLint 通过。
- API 改动文件的全文件 ESLint 仍报告 3 处既有问题：repository 中两处不必要类型断言，以及 service 测试中一处旧断言的 any 赋值。已核对 HEAD 原有相同代码，本轮没有新增这些问题，也没有清理无关代码。
- 浏览器使用现有刘洋公司管理员账号检查客户表页面、正常字段停用确认、记录名称字段禁止停用、列表说明；检查桌面及 390px 手机确认框。公司配置保持草稿修订 1、发布版本 v1，没有在演示公司确认停用或发布。
- 本地服务已重新启动。未操作服务器、未推送 GitHub、未改动已有公司业务数据。登录会正常产生会话及登录记录。
