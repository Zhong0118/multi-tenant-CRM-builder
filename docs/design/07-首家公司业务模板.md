# 首家公司业务模板

版本：草案 0.1
说明：依据当前会话中的业务描述建立；实际 Excel 表头与样例数据到位后补齐字段和指标口径。

## 1. 模板定位

这家公司是通用平台的第一个业务模板，不是平台本身。它验证以下能力：

- 同一业务对象内的管理员全量视图和员工个人视图。
- 电话 Bot 与人工外呼两种线索来源。
- 线索审核、分配、转跟单、跟进活动和转客户。
- 管理员专属字段与员工只读字段。
- 从业务明细计算漏斗和员工业绩。
- 飞书和电话 Bot 通过平台集成框架接入。

## 2. 业务全景

```text
号码/名单
   ├── 电话 Bot 外呼 ──> Bot 结果 ──> 分配员工 ──> 人工审核 ─┐
   └── 员工人工外呼 ───────────────────────────────────────┤
                                                            ▼
                              无效/稍后联系 <── 线索 ──> 有效
                                                            │
                                                       转为跟单
                                                            ▼
                                  失败/流失 <── 跟单 ──> 成交
                                                            │
                                                       转为客户
                                                            ▼
                                                           客户

期刊记录 ── 员工录入 ── 管理员确认/评级

所有业务明细 ──> 统一统计口径 ──> 管理 Dashboard
```

## 3. 角色权限矩阵

| 模块/动作 | 租户管理员 | 员工 | 集成身份 |
|---|---|---|---|
| Bot 线索全部查看 | 是 | 否，只看分配给自己 | 按作用域 |
| 线索分配/改负责人 | 是 | 否 | 默认否 |
| 审核 Bot 结果 | 是 | 自己的 | 默认否 |
| 新建人工外呼 | 是 | 是，负责人自动为自己 | 可按作用域 |
| 转为跟单 | 是 | 自己有效的线索 | 默认否 |
| 查看/编辑跟单 | 全部 | 自己的 | 按作用域 |
| 转为客户 | 是 | 自己且达到成交条件 | 默认否 |
| 查看/编辑客户 | 全部 | 自己的 | 按作用域 |
| 期刊普通字段 | 全部编辑 | 自己的可编辑 | 默认否 |
| 管理员确认/最终评级 | 编辑 | 只读 | 默认否 |
| Dashboard/业绩 | 全公司 | 只看自己的摘要 | 查询作用域 |
| 导入/导出 | 是 | 否 | 否 |

## 4. 业务对象

### 4.1 线索 `lead`

系统中是一类业务对象，界面通过来源视图分成“Bot 获客”和“人工外呼”，不建立两套底层数据。

建议系统字段：

| 字段键 | 名称 | 类型 | 规则 |
|---|---|---|---|
| `lead_no` | 线索编号 | 系统 | 自动生成、只读 |
| `source_type` | 获客方式 | 单选 | `PHONE_BOT` / `HUMAN_OUTBOUND` |
| `owner_member_id` | 负责人 | 成员 | 管理员可分配；员工新增时为自己 |
| `review_status` | 审核状态 | 单选 | 见状态机 |
| `customer_name` | 客户姓名/名称 | 文本 | 必填 |
| `phone` | 联系电话 | 电话 | 必填；用于重复提示但不自动合并 |
| `requirement` | 需求 | 多行文本 | 可空，转跟单前建议填写 |
| `call_result` | 外呼结果 | 单选 | 待确认实际枚举 |
| `call_summary` | 通话摘要 | 多行文本 | Bot 可写，员工可修正需留审计 |
| `next_contact_at` | 下次联系 | 日期时间 | “稍后联系”时必填 |
| `external_call_id` | 外部通话 ID | 文本 | 隐藏；集成内唯一 |

视图：

- Bot 获客：`source_type=PHONE_BOT`。
- 人工外呼：`source_type=HUMAN_OUTBOUND`。
- 待分配：负责人为空，管理员可见。
- 待我审核：负责人为当前员工且 `PENDING_REVIEW`。
- 稍后联系：`CONTACT_LATER`，按时间排序。

### 4.2 跟单 `opportunity`

| 字段键 | 名称 | 类型 | 规则 |
|---|---|---|---|
| `opportunity_no` | 跟单编号 | 系统 | 只读 |
| `owner_member_id` | 负责人 | 成员 | 决定员工数据范围 |
| `customer_name` | 客户姓名/名称 | 文本 | 从线索复制，可修改 |
| `phone` | 联系电话 | 电话 | 从线索复制 |
| `requirement` | 客户需求 | 多行文本 | 必填 |
| `stage` | 当前阶段 | 单选 | 使用稳定选项键 |
| `expected_amount` | 预计金额 | 金额 | 可空 |
| `next_followup_at` | 下次跟进 | 日期时间 | 跟进中阶段建议必填 |
| `loss_reason` | 流失原因 | 单选/多行 | 流失时必填 |
| `source_lead_id` | 来源线索 | 系统关系 | 只读 |

建议初始阶段：

```text
NEW → CONTACTING → NEED_CONFIRMED → QUOTING → WAITING_CONFIRMATION
                                              ├── WON
                                              └── LOST
```

阶段名称在收到现有表头与业务规则后调整；数据库保存稳定 key，不保存可变中文标签作为规则条件。

### 4.3 客户 `customer`

| 字段键 | 名称 | 类型 | 规则 |
|---|---|---|---|
| `customer_no` | 客户编号 | 系统 | 只读 |
| `owner_member_id` | 负责人 | 成员 | 默认继承跟单负责人 |
| `name` | 客户姓名/名称 | 文本 | 必填 |
| `phone` | 联系电话 | 电话 | 必填或按样表调整 |
| `requirement` | 服务需求 | 多行文本 | 从跟单复制 |
| `service_status` | 服务状态 | 单选 | 待业务确认 |
| `source_type` | 最初来源 | 系统 | 追溯到线索 |
| `source_opportunity_id` | 来源跟单 | 系统关系 | 只读 |
| `converted_at` | 转客户时间 | 系统时间 | 统计成交时间 |

客户详情显示线索来源、跟单过程和全部活动，但不复制活动为多个字段。

### 4.4 期刊 `journal`

在收到真实表头前只固定权限结构：

| 字段键 | 名称 | 权限 |
|---|---|---|
| `owner_member_id` | 负责人 | 管理员编辑；员工自己的可编辑/系统默认 |
| `journal_name` | 期刊名称 | 管理员编辑；员工编辑 |
| `journal_date` | 日期 | 管理员编辑；员工编辑 |
| `admin_confirmation` | 管理员确认 | 管理员编辑；员工只读 |
| `final_rating` | 最终评级 | 管理员编辑；员工只读 |

其他数量、金额、状态和备注字段按样表补充。管理员字段不仅在前端只读，模块权限、字段权限、导入和 API 都必须拒绝员工写入。

## 5. 状态机与动作

### 5.1 Bot 线索

```text
RECEIVED
  → PENDING_ASSIGNMENT
  → PENDING_REVIEW
      ├── QUALIFIED → CONVERTED
      ├── INVALID
      └── CONTACT_LATER → PENDING_REVIEW
```

规则：

- Bot 创建线索时以 `external_call_id` 幂等。
- 未分配记录员工不可见。
- “通过”使线索变为 `QUALIFIED`；转换动作另行确认，便于补全必要字段。
- “稍后联系”必须设置时间，并进入员工待办。
- 无效必须选择原因；不永久删除。

### 5.2 人工外呼线索

```text
DRAFT → CONTACTED
          ├── QUALIFIED → CONVERTED
          ├── INVALID
          └── CONTACT_LATER → CONTACTED
```

员工新增时负责人固定为自己；租户管理员可代录或重新分配。

### 5.3 跟单

- 每次沟通新增 `record_activity`，不得覆盖历史。
- 活动可更新下一次跟进时间；状态变化自动追加系统活动。
- `WON` 之后显示“转为客户”；重复点击返回已创建客户。
- `LOST` 需要流失原因，记录仍可查且参与流失统计。
- 重新开启流失跟单需管理员或明确权限，并记录原因。

## 6. 转换规则

### 6.1 线索转跟单

前置条件：线索有效、有负责人、客户名称存在，且未转换。

映射：

```text
lead.customer_name       → opportunity.customer_name
lead.phone               → opportunity.phone
lead.requirement         → opportunity.requirement
lead.owner_member_id     → opportunity.owner_member_id
lead.id                  → opportunity.source_lead_id
```

转换在一个事务内创建跟单、建立关系、更新线索状态并写审计。字段映射快照随转换记录保存。

### 6.2 跟单转客户

前置条件：跟单阶段为 `WON`，存在负责人和必要客户字段，且未转换。

在确认弹窗中按电话/名称展示潜在重复客户：

- 选择现有客户：建立关系，不新建客户。
- 确认新建：创建客户并继承来源。
- 取消：跟单保持 WON，之后可继续转换。

不得根据电话自动静默合并客户。

## 7. 页面与视图

### 7.1 Bot 获客

```text
Bot 获客                                      [批量分配]
[待分配] [待审核] [有效] [稍后联系] [无效]

客户        Bot 意向   摘要              负责人   状态      时间
张先生      有兴趣     计划 9 月启动…     张三     待审核    10:30
```

详情抽屉首屏展示通话结果、摘要、录音/通话链接（如供应商提供）、负责人和审核按钮。

### 7.2 人工外呼

```text
人工外呼                                      [＋新建拨打]
[我的] [稍后联系] [有效] [无效]

客户        电话      需求摘要      结果      下次联系
```

提交“有意向”后显示“转为跟单”；无意向时要求原因；稍后联系进入工作台。

### 7.3 跟单

表格主列：客户、负责人、阶段、预计金额、下次跟进、最近活动、更新时间。详情使用账本轨和活动时间线。管理员有全部/员工筛选，员工固定“我的跟单”。

### 7.4 客户

表格主列：客户、负责人、服务状态、来源、转客户时间、最近活动。详情显示客户信息、服务信息、完整来源和历史活动。

### 7.5 期刊

员工视图中管理员确认和最终评级以正常可读文本显示，并标注“由管理员填写”。管理员可在详情中编辑，也可在严格校验下批量确认。

## 8. Dashboard 与指标

以下为候选口径，待样表确认后定稿：

| 指标 | 建议口径 |
|---|---|
| Bot 外呼数 | 统计期内 `source_type=PHONE_BOT` 的唯一外部通话/线索数 |
| 人工外呼数 | 统计期内人工外呼活动或线索数；两者只能选一种口径 |
| 有效线索数 | 统计期内首次进入 `QUALIFIED` 的线索数 |
| 跟单数 | 统计期内由线索转换创建的跟单数 |
| 成交数 | 统计期内首次进入 `WON` 且完成转客户的数量 |
| 成交金额 | 成交时确认金额之和；字段与退款规则待确认 |
| 线索有效率 | 有效线索数 / 已完成人工判断的线索数 |
| 成交转化率 | 成交数 / 进入跟单数，使用相同 cohort 或明确周期口径 |
| 逾期跟进 | `next_followup_at < now` 且跟单未 WON/LOST |

员工业绩默认按动作发生时负责人计算；若历史负责人变化，转换记录保存当时负责人以稳定历史报表。

## 9. 飞书集成（平台能力，模板使用）

### 9.1 平台层

通用飞书适配器负责：

- 租户安装/授权配置。
- 飞书用户与租户成员映射。
- 消息事件验签、去重、限流和审计。
- 统一调用 Authorization 和 Records 服务。
- 卡片/消息回复及失败重试。

不按管理员和员工分别创建机器人。一个租户可以使用一个机器人实例，实际权限来自发消息者映射到的租户成员及其权限。

### 9.2 首家公司后续命令

候选只读命令：

- “我的待跟进有哪些？”
- “今天有哪些逾期跟单？”
- 管理员：“今天各员工成交情况？”

候选写入命令：

- “给客户 ABC 新增跟进：已发送报价，周五再次联系。”
- 审核后创建人工外呼记录。

写入命令先解析为结构化预览，由用户确认后提交；涉及转换、批量操作和管理员字段时默认不在机器人首期开放。

## 10. 电话 Bot 与自动化（首家公司后续）

电话 Bot 是外部外呼供应商，不与飞书机器人混为一谈。适配器接收：

- 外部通话 ID、号码、开始/结束时间。
- 接通结果、意向分类、摘要、录音引用。
- 供应商签名和事件时间。

处理流程：验签 → 幂等检查 → 号码规范化 → 创建/更新 Bot 线索 → 写集成事件 → 通知待分配或待审核。

首批自动化只建议：

- 下次跟进到期提醒。
- Bot 线索待分配提醒。
- 转换和成交通知。

自动分配、自动转换、AI 自动评级在积累真实数据与规则前不做。

## 11. 交付阶段

### Phase 1：平台安全底座

登录、租户、成员、三角色、权限、审计和 RLS。

### Phase 2：配置与通用数据工作台

业务对象、字段、表格、动态表单、详情抽屉、活动、ALL/OWN 与字段权限。

### Phase 3：首家公司核心闭环

人工/Bot 来源视图、审核、分配、线索转跟单、跟单活动、转客户。

### Phase 4：运营能力

期刊、Dashboard、导入导出、附件和指标核对。

### Phase 5：飞书

账号映射、机器人查询、提醒，再逐步开放确认式写入。

### Phase 6：电话 Bot 与自动化

供应商 Webhook、通话数据、AI 摘要和受控自动化。

## 12. 样表到位后的更新步骤

1. 为每张 Excel 标注其业务对象、负责人列和唯一/重复判断字段。
2. 把重复的员工个人表合并为一个对象和多个 OWN 视图。
3. 区分主记录字段、追加活动和统计派生值。
4. 为每个字段确定类型、必填、选项、权限、默认值和清洗规则。
5. 用 20–50 条脱敏数据试导入，确认异常值和重复规则。
6. 由业务负责人确认状态机、转换条件和指标口径。
7. 更新本文件的数据字典后，才编写数据库种子和实现任务。

## 13. 首家公司验收场景

1. 管理员给张三分配 Bot 线索，李四不能看到；张三审核通过并转为跟单。
2. 张三为跟单追加三次活动，历史顺序完整，管理员实时可见。
3. 张三将 WON 跟单转为客户，重复点击不会新建第二个客户。
4. 管理员把记录转给李四后，张三失去编辑权，历史活动仍显示原操作者。
5. 员工尝试通过 API 修改期刊最终评级被拒绝，管理员可以修改且有审计。
6. Dashboard 成交数下钻后与明细数量一致。
7. 飞书身份映射为员工时只返回其 OWN 数据；管理员身份可返回全公司数据。
8. 电话 Bot 重复发送同一通话事件时只产生一条线索或一次幂等更新。
