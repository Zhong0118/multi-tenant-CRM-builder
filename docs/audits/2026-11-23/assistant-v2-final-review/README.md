## 两条验收原句为什么拿不到筛选

在修复前，用真实模型重跑原句，记录筛选模型的输出和列表校验器的返回。两次都调用了 `preview_filter`，负责人都正确输出为 `$owner in ["$me"]`。第二句也带回了 `stage in ["quote","negotiate"]`。两次模型都把 `amount gt` 的阈值写为 JSON 字符串 `"100000"`。该表的金额字段类型为 `NUMBER`。列表校验器在检查类型时抛出 `RECORD_FILTER_INVALID`，因此返回 `unavailable`；尚未执行原话中的数值依据检查。

修复后，模型按可见字段类型生成阈值，适配器也能将无损的十进制字符串转换为 `NUMBER`。不能无损转换的值仍交给列表校验器拒绝。精确金额字段 `MONEY` 继续使用十进制字符串。两个原句分别通过真实模型定向复测，均返回一份可以在表格中应用的 `rule`。

| 原话 | 实际规则，条件之间均为「且」 |
| --- | --- |
| 找我负责的、金额超过 10 万的客户 | 负责人是我；金额大于 100000 |
| 找我负责的、报价或谈判中、预计金额超过 10 万的客户 | 负责人是我；阶段为报价或谈判；金额大于 100000 |

## 评测的变化

- 助手开发集新增真实发布的「跟单商机」业务表，其金额字段为 `MONEY`。明确的筛选请求按完整规则评分，`unavailable`、缺少条件、值类型错误都算失败。旧评分曾将两个没有规则的结果判为通过。
- 「帮我筛选」要先成功读取当前表的可见字段，评分逐个比较选项和这次读取返回的合法方向。独立的隐藏字段回归在隔离库中执行，未加入冻结留出集。
- 一句话筛选开发集 **17/20**。多条件、选项与金额 4/4，三项失分均为澄清候选的解释或组合与标注不符。独立的无效输出权限检查 **6/6**。[逐例结果](nl-filter-development.md)
