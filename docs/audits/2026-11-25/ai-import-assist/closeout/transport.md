# AI 导入连接失败排查

上轮四组正式 JSON 有四次 `AI_APICallError` 和一次超时。SDK 错误本身可以携带 URL、请求正文与响应正文。此前运行器只取错误名，因此无法还原每次失败的具体连接错误或 HTTP 状态码。[上轮调用明细](../eval-calls.md)

| 文件 | 耗时 | 原始分类 |
| --- | ---: | --- |
| d03 | 5.537 秒 | AI_APICallError |
| d28 | 5.521 秒 | AI_APICallError |
| h11 | 5.545 秒 | AI_APICallError |
| h21 | 5.544 秒 | AI_APICallError |
| h26，第三次配对运行 | 25.033 秒 | timeout |

生产出站通道为 Undici 连接设定了 5 秒超时，结构化生成调用的 SDK 重试次数为零。在本机复现实验中，一个回环 TCP 服务接受连接并保持 TLS 握手未完成，客户端沿用同版本 Undici、相同连接超时和 Responses SDK。仅调用一次，SDK 在 **5.521 秒**返回 `AI_APICallError`，错误链为 `UND_ERR_CONNECT_TIMEOUT`、可重试、无 HTTP 状态码。直接调用 fetch 测得 5.506 秒。这解释了旧记录中约 5.5 秒的聚集；单凭耗时无法给四笔历史记录分别定因。

本轮在导入生成层包住一次完整且独立计量的请求。HTTP 429、5xx 和已识别的瞬态网络错误使用同一配置、调用预算和中止信号再尝试一次。两次调用合计最多 25 秒。每次失败只保存状态码、错误分类、是否可重试和尝试序号。SDK 的原始报错、请求正文与响应正文不进入日志。评测另外在物理发送点数出实际重试次数，包含成功恢复的尝试。
