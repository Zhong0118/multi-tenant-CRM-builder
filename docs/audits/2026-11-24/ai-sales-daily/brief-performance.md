# 个人清单查询与权限验收

2026-11-24 在本机独立 PostgreSQL 库执行。清单通过 Nest 的真实 HTTP 监听端口、登录会话、工作区守卫、租户数据库角色和权限解析。每个请求重新计算清单。

| HTTP 入口 | 首次请求 | 预热后 p50 | 预热后 p95 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| 个人清单首屏，每组前五 | 137.03 ms | 131.11 ms | 196.17 ms | 217.50 ms |
| 数量最大的关注组「进展停滞」，抽屉第一页 | 62.36 ms | 157.55 ms | 253.42 ms | 342.61 ms |

每个入口单独预热 10 次，再以并发 10 执行 200 次。p95 取排序后第 190 项。首次请求使用本次启动的 API、刚完成造数和 ANALYZE 的数据库，未清空操作系统或 PostgreSQL 文件缓存。各组去重后有 487 条逾期、697 条回收、1,822 条停滞、1,454 条久未联系。两个入口的 p95 均低于 300 ms。

## 规模与方法

- Apple M4，10 核，16 GiB 内存。PostgreSQL 15.19，数据库 102 MB，shared_buffers 128 MB，work_mem 4 MB，default_statistics_target 100。造数后执行 ANALYZE。
- 同租户 50,000 条记录，登录成员负责 5,002 条。约七成新增记录集中在另一位员工。线索表按本人范围读取，发票表可读全表。跟进任务允许指向同事负责的可读记录。
- 源数据包括 24,999 条历史沟通、16,666 条已完成跟进、1,219 条逾期跟进、6,666 条流转历史。固定取模公式分配负责人、表、日期和回收期限。测试库管理员仅在批量造数事务内关闭触发器，避免伪造的历史活动触发现实时间的新提醒和回收操作。业务查询始终由普通数据库角色执行。
- 初版在同一批候选上重复执行联系时间和状态时间的相关子查询。包含四组的数据集测得首屏和抽屉 p95 分别为 567.07 ms、550.17 ms。最终查询先合并本人记录与本人到期跟进的目标，排除无权限和终态，再只为仍需判断的记录求状态和联系时间。组间按优先级去重后才计数和分页。
- 状态历史命中新增的 tenant/record/to_state_key/created_at 索引，完成跟进命中 tenant/record/completed_at 部分索引，沟通走现有的 tenant/record/created_at 索引。回收期限在已经限定到本人的记录上求值。单次 EXPLAIN ANALYZE 执行时间分别为 44.86 ms、45.27 ms。[完整计划与缓冲读取](brief-query-plans.txt)

## 复跑

给已应用分支迁移的独立本机测试库设置 TEST_DATABASE_URL 和 TEST_DATABASE_ADMIN_URL。基准会重建 critical-a、critical-b 测试夹具，结束时清理。原始采样摘要和查询计划写入 BRIEF_BENCH_REPORT 指定的临时文件。

```sh
BRIEF_BENCH_REPORT=/tmp/daily-brief-bench.json pnpm --filter @crm/api test:e2e --runInBand --testRegex daily-brief.bench.ts
pnpm --filter @crm/api test:e2e --runInBand test/daily-brief.e2e-spec.ts
```

HTTP 用例验证无套餐清单、四组条件、终态和他人隔离、同事记录上的本人跟进、按 ID 游标翻页、日切、设置即时生效与版本冲突。模拟模型覆盖首次生成并发合并、零模型缓存读取、未发送不占次数、已发送失败保留旧结果、第三次重生成后的封顶。真实角色检查同租户他人、跨租户身份、兼有平台身份的公司管理员对他人缓存均不可见，关闭套餐后本人的缓存也不可直接读取。
