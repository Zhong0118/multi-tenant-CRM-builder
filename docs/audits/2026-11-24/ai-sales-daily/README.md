## 销售拿到的文案

- 校验删除或替换的原文句子，占开发集 2/135（1.5%）、留出集 0/37。以模型原始正文句子为分母，校验后还能逐字找到即保留。邮件主题单独校验。早期提示词和校验搭配曾达到 174/182；修改生成要求后，又对金额、日期和承诺分别校验并补上回归用例。
- 在可交付文案中，客户名称逐字出现的比例为开发集 28/29、留出集 9/9。按提示词的段数要求计，短文 2–3 段、中文案 3–5 段，达标分别为 18/29、6/9。邮件称呼、落款、程序补充的拜访概况均算一段。把标题和落款分别输出容易让短文超长。
- 语气和可用性由 Codex 阅读校验后的文案，对照业务描述、文体和指定语气打分。分层抽查开发 1–4、留出 1、3、4、6，覆盖消息、邮件、电话提纲、拜访准备。7/8 语气合适，开发 4 要求亲切，实际更像工作记录。按「事实方向正确、语句自然、直接发送或当场照用」计 5/8。开发 3、留出 6 需要补报价，开发 4 的「概况：名称」不自然。此项为模型抽查，销售人员尚未评分。
- 对照 38 份成功输出及其输入，未发现凭空给出的具体金额、数量或约定日期。询问方便的时间、带占位符的报价按待确认内容计算。这一结论限于本次样本。另有措辞风险，例如留出 9 把没有标明归属的「财务」写成「我方财务」。该项通过结构检查，仍需要销售核对说话方。
- 服务端先拿完整的结构化结果、校验每个段落，再用 NDJSON 交付。首个可见正文需要等待模型生成完成。工作台没有选中的单表视图，建议上下文优先取各表已发布默认视图的可见字段。

## 权限、写入和性能

- 后端检查套餐，两个同名记录先选定目标再生成。详情写作与聊天写作都检查当前用户的字段和记录权限。真实 HTTP 验收把测试值植入隐藏字段，在模拟模型实际输入和返回的业务响应中均未出现。保存沟通、跟进和日报沿用原有入口。[浏览器验收和 26 张截图](browser/README.md)
- 5 万条记录、并发 10、每入口 200 次请求，个人工作台首屏 p95 为 196.17 ms，关注组抽屉 p95 为 253.42 ms。测试机、数据库版本、数据分布和 SQL 执行计划均已记录。[清单查询与隔离实测](brief-performance.md)
- 四项既有 AI 功能的模拟 provider 回归，与阶段 A 基线逐份比较，六份报告内容相同。对话助手开发 35/35、留出 6/15，整理沟通 13/36、5/20，一句话筛选 9/20、3/10，建表 1/23、0/10。这些数字衡量固定模拟响应对场景的覆盖。
- 迁移 0058 允许平台显式分配三项权益，0059 增加个人建议缓存、公司规则及清单索引，0060 更新输出预算。现有套餐继续使用原有功能列表。部署先应用阶段 A 和 B 的数据库迁移，再更新 API 和 Web；模型主密钥及环境变量转平台配置的操作见 [阶段 A 运行说明](../ai-models/README.md)。
