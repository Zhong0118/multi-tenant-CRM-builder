# 组长对组员记录的独立列权限验收

## 范围

- 基线：`9525410`，分支 `codex/group-record-field-access`。
- 公司管理员逐表配置组长对本组其他成员记录的列权限；本人记录保留原权限。
- 新授权仅用于普通字段修改，仍受表级修改总开关控制，不额外授予转移负责人、删除、流程确认、附件、跟进或关联管理权限。
- 新迁移 `0044_group_record_field_access` 新增可空配置并更新数据库的成交保护权限判断；不回填权限或业务数据。
- 本轮不部署服务器，不修改生产公司配置。演示数据库与自动化测试数据库相互独立，也与其他工作树使用的数据隔离。

## 实际网页验收

环境为本地 Web 3186 / API 3187，数据库 `crm_group_fields_browser_20261029`。关闭真实短信、真实 AI Provider 和公开注册。以既有演示账号刘洋、赵晨、孙悦及两条新建虚构记录测试。

1. 刘洋打开成员 → 赵晨的访问权限 → 客户，确认员工默认、本人记录、本组其他成员记录三列对照。
2. 在“设置组员列权限”中，将客户姓名和工作单位保持只读、联系电话设为隐藏、研究方向设为可编辑。保存成功，无需发布业务表。
3. 赵晨查看混合列表：孙悦的电话单元格为空，本人的电话仍正常显示。
4. 赵晨打开孙悦的记录，电话字段不出现在详情或编辑表单；工作单位只读；只有研究方向提供输入框。修改并保存，刷新后仍保留。
5. 赵晨打开自己的记录，电话、工作单位等原可编辑字段仍可编辑。
6. 孙悦打开自己的同一条记录，仍能看到电话，能看到组长保存的研究方向。组长对组员的限制没有改变孙悦自己的权限。
7. 在本地副本关闭修改总开关后重新加载赵晨的组员详情，编辑按钮消失，原可编辑的研究方向显示只读；随后恢复本地演示配置。

## 实际 HTTP 验收

父级独立脚本 `/tmp/crm-group-fields-verify.cjs` 通过以下七组检查：

- 列表、详情按当前记录负责人区分本人和组员字段。
- 明确允许的组员字段可修改；只读或隐藏字段被拒绝；混合提交整条回滚，记录版本和值不变化；负责人转移仍被拒绝。
- 隐藏的组员电话不能用作筛选、排序、搜索或导出；导出保留本人有权读取的电话。
- 普通组员本人权限保持不变，不能反向读取组长记录。
- 关闭表级修改总开关后，组员列编辑立即被拒绝。
- 隐藏组员标题字段后，组员记录不可读，本人记录仍可读。
- 移出组员后，后续请求立即不可读；测试完成后恢复本地演示分组。

## 复核中补修的边界

- AI 操作预览和确认按实际记录列权限处理；缓存投影同时读取可读性与负责人，避免两次读取间的权限变化。
- 不允许空的组员字段修改触发版本更新或自动化。
- 权限映射采用自身属性检查，合法字段名 `constructor` 不会读取 JavaScript 原型属性。
- 组员字段修改命中无权执行的自动化时，整次失败并提示原因；一次性规则已执行的情况下也不能绕过该边界。
- 只读文案使用“当前只读”，避免把组员本人可编辑误写成“仅管理员可编辑”。
- 导入普通映射保留本人可编辑字段；查重字段只提供当前查询范围共同可见的列。
- 本人标题隐藏而组员标题可见时，“仅本人”范围不能绕过读取限制；公共池分类计数不会让合法组员列表整体失败。
- 使用独立组员列策略的 AI 历史记录捕获权限修订信息。权限、公共池可见性或归属变化后，历史正文、来源及工具摘要均重新限制；普通值更新和未使用该功能的普通会话保持原行为。撤销策略后的新普通回答与旧受保护回答逐条处理，不受分页混合影响。
- AI 完成写入绑定服务端的尝试编号，并以原消息元数据原子比较后写入，迟到的旧尝试不能覆盖重试结果或套用新的权限修订信息。

AI 历史的保守限制依赖应用及数据库回收任务已有的事务审计，不覆盖绕过审计的超级用户直接 SQL。相关安全事件发生在同租户其他数据上，也可能使受保护的历史回答需要重新查询；不删除原文，显示固定说明，用户发出的消息保持不变。
