### 金额兼容的边界

读取历史 numeric MONEY 时，直接使用 PostgreSQL `->>` 提取数据库保存的十进制文本，不把经 Prisma 解码的浮点数当成原始金额。一次批量补读覆盖一页记录，保留 tenant/object/id/version 约束；如果两次读取间版本发生变化，返回既有版本冲突而不是混用快照。没有 N+1 查询。

只读和预览不改数据库；用户显式保存或执行开单动作时，既有整份 JSON 更新会把历史 numeric MONEY 归一为字符串，**金额不变，存储表示可能改变**，包括保留的隐藏/停用金额字段。这不是批量数据迁移。无法恢复写库前已经丢失的精度；测试用 SQL 原始 JSON 数字验证 `100000000000000.01` 和 `9007199254740993`，没有先在 JavaScript 中舍入测试数据。


## 扩大回归发现的同类查询问题

- 数字/金额排序的 `data ->> key::numeric` 缺少括号，PostgreSQL 解析成错误运算，实际返回 500。改为 `(data ->> key)::numeric`。
- 默认排序下的数值范围筛选把 `Prisma.Sql` 当成 `WhereInput` 使用，实际报 `Unknown argument values`；数值范围改走已有参数化 SQL 路径，支持原系统排序和字段排序，继续保留公司/负责人/公海/分页条件。
- 空值与非空值筛选也使用了同样的 SQL/ORM 混用写法，纳入同根回归和修复。
- SQL 列表先查 ID、再读行，两次读取之间被转交的记录可能以新负责人/新内容返回给旧负责人。二次读取必须继续匹配租户、归属及最初版本；变更时返回冲突，避免跨归属读取。此竞态原字段排序路径已存在，本轮新增受控数据库回归。

## 网页完整流程与数据保护

在独立数据库副本，用既有公司管理员与员工演示账号操作已配置的客户、合同、询单字段、跨表规则和保护依据。没有修改原本地库、其他 UI agent 的数据库或生产服务。

1. 管理员新增无负责人客户，进入线索公海；旧记录不自动入池。
2. 员工预览并领取，成为负责人，开始 24 小时联系期限。
3. 确认建立联系，进入 FOLLOWING，开始 720 小时（30 天）跟进期。
4. 标记询单、保存并刷新，字段保留；询单不续期、不停止回收。
5. 追加有内容的跟进活动，最近跟进及回收期限更新；普通编辑和未来待办不续期。
6. 员工预览并生成关联开单，金额正确、负责人沿用，客户仍在跟进期。
7. 管理员确认签约，正式流程状态和普通合同状态一起更新；客户进入 PROTECTED，保留负责人、清空回收期限。
8. 员工刷新后没有释放入口，关联仍可返回订单。
9. 管理员打开已有历史金额记录，编辑框有正确金额；取消编辑，不保存旧记录。

所有补修构建后，再完整执行了一轮上述流程。排除本轮专用新增样例后，逐行内容摘要核对确认已有记录与业务表配置不变。具体记录、身份、内容摘要和截图只保留在本地验收材料，不提交 GitHub。

没有等待真实 24 小时或 30 天；到期回收、重复领取、权限拒绝、原子回滚与重复执行由真实数据库 HTTP 测试覆盖。本轮临时网页/API 验收进程已关闭，未停止其他任务服务。
