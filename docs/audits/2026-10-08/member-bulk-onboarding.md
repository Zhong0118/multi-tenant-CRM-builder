# 员工批量邀请与公司名册验收

## 使用方式

公司管理员进入「成员管理」→「批量邀请」，粘贴带表头的名单或上传 UTF-8 CSV。表头为姓名、手机号、角色，角色可省略或留空（默认员工），允许员工/普通员工/公司管理员。每批 1–100 人、文件不超过 1 MiB。先校验预览，再确认邀请；失败逐行显示，重试仅处理失败行。

示例：

```csv
姓名,手机号,角色
张三,13800138000,员工
李四,13900139000,公司管理员
```

邀请不会自动发送通知短信。管理员复制页面提供的注册链接给员工；新员工使用受邀手机号获取验证码、设置自己的密码，登录后接受邀请。已有账号直接登录接受邀请。公开注册仍关闭，仅符合受邀/首个管理员规则的手机号可注册。

名册勾选当前页员工后可批量改角色、恢复、停用；不允许选择自己。翻页清空选择。停用前需完成记录和待办交接，仍保护最后一位可用管理员。姓名在每行「修改姓名」中维护，仅影响当前公司的名册和业务显示，不修改个人账号或其他公司姓名。手机号及密码归个人账号，管理员不能批量覆盖。

## 实现与问题修复

- 迁移 0024 为成员和邀请分别增加可空 display_name，历史记录回退个人姓名，接受新邀请时复制公司姓名。
- 名称修改执行当前管理员复核、租户隔离和审计；记录负责人、跟进和看板优先展示公司姓名。
- 拒绝给已入职或已停用成员重复创建邀请，停用成员应恢复使用。
- 独立 review 发现 tenants FOR UPDATE 在普通成员 RLS 下不锁行。创建邀请及接受邀请现共享租户 advisory transaction lock，避免并发接受后产生多余 PENDING 邀请。保留原 Serializable 冲突重试。
- 批量采用现有单条受保护 API 顺序调用，无新队列或全批回滚。操作中的名单、动作、关闭按钮锁定；逐行保留结果，只重试失败。

## 本地证据

- API 全仓单测：100 suites / 1303 passed（原有 3 skipped）；Web 88 files / 662 passed；其他包通过。
- 最终相关 API 单测 4 suites / 27 passed；Web 成员与共享 CSV 6 files / 32 passed。
- Critical API + auth persistence：14 passed，独立 PostgreSQL 18 数据库、24 migrations、受 RLS 约束 crm_app。
- 真实 HTTP 覆盖受邀注册（关闭公开注册）、接受、不同公司姓名隔离、全局账号姓名不变、员工/跨租户/空白姓名拒绝、重复/停用成员邀请拒绝及启停。
- 并发回归：修前接受请求绕过 advisory lock，测试失败；修后 pg_locks 观察到等待，再释放并成功接受。
- 全仓 typecheck 通过；受影响成员产品代码 ESLint 通过。既有 critical E2E 文件含旧 Supertest any lint，新增代码不扩充该问题。
- Chromium 1440/900/390：页面无横向溢出，抽屉内容内部可滚动，批量成功/失败提示、公司姓名保存、批量角色变更与列表刷新通过，pageerror 为零。
- 使用隔离数据和开发验证码，没有新增生产测试账号或发送真实短信。
