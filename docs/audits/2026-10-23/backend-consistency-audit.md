## 实际修复的五个问题

### 1. 发布后旧标题仍可泄露原字段内容

更换标题字段、隐藏原字段或修改单选标签后，元数据更新了，但 `records.title` 缓存不变。详情、搜索、导出、关联与 AI 可能继续消费旧标题。

修复：在发布事务及既有配置排他锁内，根据新标题字段与单选标签重建该对象的标题，仅更新发生变化的缓存；不改业务数据、记录版本和修改时间。新标题超长则阻止发布并整体回滚。历史缓存会在该表下一次成功发布时重建；本轮没有在生产批量重写标题。发布会扫描该表记录，大数据量的发布耗时需在后续上线验收中观察。

证据：修复前测试得到 `private-former-title` 而非新标签；修复后覆盖详情、搜索旧值不可命中、新标签可搜索、导出、长标题回滚。

### 2. 停用后恢复字段可绕过历史选项保护

原校验只比较当前已发布的字段。字段停用并发布后不在当前快照，恢复时删除历史选项可绕过检查。

修复：用各字段最近的历史发布定义保护选项；当前版本差异仍只对当前快照计算，恢复仍正确显示为添加，不重复显示已停用字段变更。选项应停用而非删掉历史身份。

### 3. 平台模板复制公司成员默认值

MEMBER 默认值是某公司的成员 ID，原模板发布和应用可能直接复制到另一家公司，形成无法通过成员校验的默认值。

修复：模板发布与应用双入口拒绝非空的 MEMBER 默认值，包含以前已发布的有问题版本。成员字段本身可继承；具体默认成员须在目标公司初始化后配置。公司自己的成员默认值能力保持不变。

### 4. 日报无效日期被归一化后进入数据库

`Date.parse` 会把某些不存在的月末日期归一化，例如 2 月 30 日，并接受 PostgreSQL 不支持的 0000 年。原校验误接受输入，后续数据库日期转换失败。

修复：增加日历日期往返校验，GET/PUT 对非法日期返回输入错误，有效闰日保持可用。

### 5. 自动化创建记录绕过公海初始化

普通新建会设置公海阶段和期限，Actions 的 CREATE_RECORD 直接调用底层创建命令，导致自动化目标表启用公海时，新记录虽有负责人但没有阶段、领取时间和回收期限。

修复：提取并复用现有初始化函数，手动触发和字段变更触发自动化都使用目标表的期限配置。权限、原子事务、关联和去重机制保持原有实现。导入仍尊重用户明确选择的归属方式，历史记录不自动转换。

## “询单”的确认规则与配置建议

用户已确认：客户明确提出需求或询价后，由员工手动标记进入询单。

1. 保留一张客户表及原有公海系统阶段：初始公共池、待联系、跟进中、已联系公共池、成交保护。不新建重复客户表。
2. “询单中”属于业务进度，可用现有单选字段配置选项，并允许负责员工编辑。如果已有合适字段就增加选项，不重复建字段。字段草稿保存后需要发布。
3. 员工成功联系后确认联系，或登记带“已接通/已添加微信”结果的活动，待联系记录进入跟进期。只有一条普通备注不等于确认建立联系。
4. 询单仍处于 FOLLOWING 的持有/回收机制内，默认 30 天；有效活动继续按现有规则续期。仅改变“询单中”字段不冒充一次跟进。
5. 确认订单或签约后才使用成交保护。需要先在订单/合同表发布明确的流程状态，再在客户表公海配置中绑定来源表、确认状态及关联证据。仅把客户字段改成“已成交”或把保护阶段改名不会自动建立这些证据。
6. 已失单客户可释放；无效号码、重复客户可由管理员处理。生产历史记录的归类、改名和规则配置需另行执行，不属于此次 PR 的数据变更。

UI 任务的文案交接：`record-pool.tsx` 联系确认弹窗目前写“待联系期间写活动不能代替联系确认”，与带明确成功联系结果的活动会自动确认的实际逻辑不完全一致。UI agent 应改成“普通备注不会确认联系；登记已接通或已添加微信可确认联系”，并保持后台已有行为。本 PR 不改其正在优化的页面。

## 管理员正确操作与验收

- 字段名、选项、员工基础访问范围、默认列表等配置：保存草稿 → 检查发布预览 → 发布 → 员工刷新页面核对。不要用管理员草稿页判断员工已经看到什么。
- 已发布单选不能直接变成多选。新建多选或恢复旧字段，至少启用一个选项，设置员工访问及列表列后发布；需要搬迁历史值时另作受控数据迁移。
- 模板：管理中心 → 创建公司时选择模板和已发布版本。新公司获得副本，之后按公司管理；发布新模板版本不会自动改老公司的字段或记录。
- 公海：管理员未指定负责人新建时，只有表已开启分阶段公海才进入初始公共池。普通“负责人为空”、导入旧记录与公海成员身份不能混为一谈。
- 工作统计：先在记录动态中登记电话、微信、拜访及结果；管理员查看成员统计并分配任务；员工在“任务与日报”填写执行结果和日报。没有登记就没有对应统计。
