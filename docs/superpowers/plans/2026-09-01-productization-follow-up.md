# CRM 产品化后续路线

日期：2026-09-01

状态：交接任务清单，不代表已经完成

目标：先把现有功能变得可理解、可操作，再重做工作台视觉，最后接入生产短信。

## 1. 执行原则

- 按阶段完成，不同时改排序、工作台、邀请和短信。
- 用户可见 Bug 优先于架构优化。
- 每个 Bug 只保留一个能复现原症状的聚焦验证。
- 纯视觉任务以浏览器截图和人工验收为主，不为每个 CSS 细节补测试。
- 每完成一个阶段单独提交；禁止 `git add .`。
- 不修改 `register/page.tsx`、`chat会话.md` 和旧 SDD progress。
- 不推送、不部署，除非用户明确要求。

## 2. P0：正确性修复

### P0.1 记录列表三态排序

状态：已完成（本地，未推送、未部署）。

原问题：表头从升序切到降序后，第三次点击产生 `sorter.order = undefined`，处理器直接返回，受控状态仍保留倒序。

期望：

```text
升序 → 降序 → 业务表发布时配置的默认排序
```

验收：

- 业务编号和最近更新两列均可完成三态循环。
- 恢复默认后 URL 不保留多余排序参数。
- 搜索、筛选和分页上下文不被清空，页码回到 1。

### P0.2 人工走查邀请与启用

使用一组新手机号只走一遍：创建公司、注册、接受邀请、启用、进入工作区。记录页面、按钮、错误提示和实际状态，不执行大范围自动化测试。

## 3. P1：把生命周期和空状态讲清楚

### P1.1 公司详情步骤条

公司详情展示：

1. 公司已创建。
2. 首位管理员邀请状态。
3. 管理员是否已接受。
4. 公司是否已启用。
5. 是否已有业务对象草稿、已发布对象和已发布工作台。

每一步只显示当前可执行动作。例如管理员尚未接受时，不把“启用公司”表现成普通可用按钮。

### P1.2 空公司初始化入口

超级管理员公司详情提供两个并列选项：

- 应用业务模板。
- 暂不使用模板，由公司管理员手工创建。

公司管理员空工作空间提供明显入口：`创建第一张业务表`，不能只显示空侧栏。

### P1.3 邀请反馈

- 等待页显示公司、角色、邀请人、有效期和接受后的下一步。
- 接受成功但公司仍为 DRAFT 时，明确提示“等待平台启用”，而不是像权限错误。
- 平台公司详情实时显示已接受管理员数量。

### P1.4 术语统一

- 工作空间：某家公司的独立 CRM 环境。
- 管理工作台：公司管理员首页。
- 我的工作台：员工首页。
- 设置：业务表、工作台和成员管理的配置入口。

避免出现含义模糊的“管理工作空间”按钮。

## 4. P2：真正重做管理员与员工工作台

这是视觉与产品结构重做，不是继续给现有卡片换颜色。

### 管理员首页建议结构

- 第一行：3–5 个主要 KPI，紧凑但不拥挤。
- 第二行：主趋势图占 2/3，状态分布或漏斗占 1/3。
- 第三行：员工业绩排行与需要关注的业务列表。
- 顶部提供时间范围和少量全局筛选。
- 无配置、无数据、无权限和组件失败必须有不同空状态。

### 员工首页建议结构

- 我的 KPI。
- 我的趋势或阶段分布。
- 我最近需要处理的记录。
- 快捷创建和进入常用业务表。

### 视觉验收

- 在 `nebula-demo` 的真实数据下截图对比管理员和员工首页。
- 1440px 桌面宽度下不能显得空散或像 Demo 卡片墙。
- 组件标题、主数字、辅助说明和操作入口有清晰层级。
- 允许一定圆角，但表格、工具栏和密集数据区域保留工具化的直角或小圆角。
- 不生成假业务数据填满页面。

## 5. P3：通用业务表搜索与筛选

当前搜索只查询 `records.title`，即对象标题字段派生出的稳定列；它不是默认列表第一列，也不会扫描整个 `records.data`。当前筛选只支持负责人和 `SINGLE_SELECT` 字段。

不要直接对 JSONB 所有值做模糊搜索。应根据已发布 Schema 和当前用户字段权限生成类型化能力：

- 关键词搜索：始终包含标题字段，并允许公司管理员在默认视图中选择额外的 `TEXT / TEXTAREA / PHONE / EMAIL` 搜索字段。
- 选项筛选：`SINGLE_SELECT / MULTI_SELECT` 支持多值包含。
- 成员筛选：负责人和 `MEMBER` 字段按成员 ID 查询；选择器可按显示姓名、员工编号搜索，手机号只对有权限的管理员展示。
- 日期筛选：`DATE / DATETIME` 支持日期范围和常用相对时间。
- 数值筛选：`NUMBER / MONEY` 支持等于、区间和大小比较。
- 其他筛选：`BOOLEAN` 支持是/否，文本支持包含和非空。
- 权限：`HIDDEN` 字段既不能出现在筛选器中，也不能被服务端用于该员工的搜索。
- URL：搜索、筛选、排序和分页继续保存在查询参数中，返回记录详情后能够恢复上下文。

业务列排序也属于本阶段，必须依据发布字段类型生成，不允许把 JSONB 字符串统一做字典序排序：

- `TEXT / PHONE / EMAIL`：按文本排序。
- `NUMBER / MONEY`：安全转换后按数值排序。
- `DATE / DATETIME`：安全转换后按时间排序。
- `SINGLE_SELECT`：按管理员配置的选项顺序排序，而不是按选项键排序。
- `MEMBER`：首期可暂缓；实现时按成员显示名稳定排序并用成员 ID 作为次序键。
- `BOOLEAN`：可支持，但优先级低。
- `TEXTAREA / MULTI_SELECT / ATTACHMENT`：首期不开放排序。

公司管理员继续负责选择默认列表列和默认排序；系统根据字段类型自动决定列是否可点击排序，首期不再增加逐字段“允许排序”开关。

验收：

- 业务表不同，筛选器随各自发布 Schema 自动变化，不写死线索、客户或商机字段。
- 能按成员姓名找到负责人或成员字段对应的记录，但提交给 API 的是成员 ID。
- 支持排序的业务列能完成升序、降序、恢复发布默认值三态循环。
- 普通员工不能通过搜索或筛选推断隐藏字段值。
- 大数据量下不进行无边界 JSON 全表扫描；需要的索引在真实查询计划确认后添加。

## 6. P4：侧边栏可调宽度

- 桌面端支持拖拽，建议范围 200–320px。
- 宽度写入 `localStorage`，刷新保留。
- 收起状态独立于展开宽度。
- 移动端不显示拖拽手柄。
- 双击手柄恢复默认宽度。

该项不应阻塞 P0/P1。

## 7. P5：唯一性和命名规则

当前公司代码全局唯一、对象代码租户内唯一、手机号全局唯一；公司名称允许重复。

建议：

- 保持公司代码全局强唯一。
- 公司名称先做重复警告，不立即增加数据库强唯一，避免同名主体或分支机构无法创建。
- 页面明确告诉管理员业务对象的稳定标识是 `tenantCode + objectCode`。
- 登录继续使用唯一手机号；显示姓名允许重复。

若用户坚持公司名称强唯一，再单独设计规范化规则和迁移，不在普通表单校验里偷偷实现。

## 8. P6：真实短信验证码

### 已有基础

- 验证码只存哈希。
- 10 分钟过期。
- 最多五次错误。
- 手机号、IP、设备频率限制。
- 使用后一次性消费。

### 待实现

1. 定义生产 `VerificationSender` 适配器。
2. 接入选定供应商 SDK 或官方 HTTP API。
3. 注册与找回密码使用不同模板。
4. 环境变量校验和启动失败提示。
5. 供应商错误映射、超时和有限重试。
6. 日志只记录请求 ID、用途和脱敏手机号，禁止记录验证码与密钥。

### 用户必须提供

- 短信供应商。
- AccessKey / Secret。
- 审核通过的签名。
- 注册模板 ID。
- 找回密码模板 ID。
- 模板变量名。

密钥只进入本机或部署环境变量，不能写入 Markdown、源码或 Git。

## 9. 后续独立切片

以下内容不要混进上述阶段：

- Excel 导入预览、字段映射、类型转换、错误行回执。
- 记录活动时间线。
- 状态机和记录转换。
- 对象关系。
- 批量修改、导出和个人视图。
- 平台日志、后台任务和系统设置。

## 10. 推荐交接顺序

1. 完成 P0.1 排序修复。
2. 人工完成 P0.2 邀请/启用走查并记录真实问题。
3. 一次性完成 P1 的生命周期 UX。
4. 使用浏览器截图驱动 P2 工作台重做。
5. 完成 P3 通用搜索与筛选。
6. 有余力再做 P4 侧边栏宽度。
7. 用户提供短信参数后单独执行 P6。

不要在短信参数缺失时先写一个假生产实现，也不要在 P1 流程仍不清楚时继续堆工作台组件。
