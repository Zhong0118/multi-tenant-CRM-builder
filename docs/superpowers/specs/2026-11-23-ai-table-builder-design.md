# AI 建表 V1 设计（待审）

基线为合并 PR #84 后的 `main@f89f3f8`。刘洋从业务表管理页描述设备租赁业务，预览客户、合同、设备、回款四张表，删除一张、调整合同字段，确认后得到三张草稿。此时赵晨的导航和已经发布的结构均保持原状。刘洋配置员工权限、检查发布分析并点击发布后，赵晨按实际授权操作。

## 与现有代码对齐的三个决定

1. **员工权限沿用手动新建的实际默认值。** 有初始字段时，`ObjectsService.create` 将增、读、改、删都置为 false，读写范围均为 NONE，所有字段 HIDDEN。「销售只能看自己的」在预览中列为管理员待配置的意图。AI 直接赋予 OWN 会扩大权限。验收 1 展示意图和实际值；验收 2 添加一次明确的手动授权，再验证员工能建记录。必填隐藏字段无有效默认值时，现有发布分析会阻止发布。创建草稿允许保留该提示，与手动创建一致。[建表与权限](../../../apps/api/src/modules/objects/objects.service.ts) · [发布校验](../../../apps/api/src/modules/objects/object-configuration.policy.ts)
2. **MEMBER 是第十二种可发布类型之一，但新建 DTO 的初始字段不接受它。** 标题取现有发布规则支持的必填类型。先用初始字段创建含标题的草稿，再用已有的新增字段方法写入 MEMBER，最后设列顺序和权限。成员字段可以是「技术顾问」，平台内置的「负责人」另行处理。[字段集合](../../../apps/api/src/modules/objects/object-schema.ts) · [手动 DTO](../../../apps/api/src/modules/objects/dto/object.dto.ts)
3. **推广现有整组发布。** 模板入口用真实的 templateVersionId 查候选，AI 表没有模板版本。保留模板入口的整组完整性检查；给 AI 草稿增加显式选择一组草稿的入口，让两者共享原有的锁、版本、分析、提交和审计。创建草稿与发布是两个独立的管理员动作。[现有组发布](../../../apps/api/src/modules/objects/objects.service.ts) · [现有组页面](../../../apps/web/src/features/objects/template-initialization.tsx)

## 蓝图契约与模型边界

以下为拟新增的交换格式。服务端在预览中分配稳定的临时 ID；UI 和单表调整用这些 ID 引用表、字段、选项。重命名和重排不会改变身份。编码、选项键、默认权限等执行值在服务端产生。

```ts
type Blueprint = {
  version: 1
  tables: TablePlan[]                         // 创建时 1–6
  assumptions: string[]
  omitted: { request: string; reason: string; alternative?: string }[]
}
type TablePlan = {
  id: string; name: string; description?: string; icon?: string; reason: string
  fields: FieldPlan[]                         // 含标题，合计 1–40
  titleFieldId: string
  view: { columnIds: string[]; reason: string }
  employeeIntent: { request: string; reason: string }[]
}
type FieldPlan = {
  id: string; label: string; type: PublishedFieldType; required: boolean
  options?: { id: string; label: string; reason: string }[]
  validation?: FieldValidation                // 沿用手动配置按类型允许的键和值
  reason: string
}
type Issue = {
  tableId?: string; fieldId?: string; path: string
  code: string; message: string; blocking: boolean
}
```

- `generateTableBlueprint` 使用 provider 的结构化输出。输入有模式（新建、调整某表、补字段）、管理员原话、相关表名及字段摘要、内置能力、允许类型与限制。调整时附被选中的草稿和当前编辑值。只发送本租户建表所需的结构元数据；不读取业务记录、附件内容、人员名册或密钥。上下文超出预算时请管理员限定范围，完整重名检查始终在服务端做。
- 模型输出候选名、说明、类型或不支持的意图、标题和列的本地引用、逐项理由、权限诉求及未采纳项。系统提示要求区分字段语义，保留明确请求，用未采纳项解释公式、关联等需求。模型不能选择租户、已有表 ID、系统字段标志、执行权限或最终编码。未知类型返回带路径的问题，无法解析的整份输出允许重试。假设和理由均按普通文本展示。
- 规范化后的表名、图标、标题及初始字段投影至 `CreateObjectDefinitionDto`。说明通过已有的更新表定义方法写入；视图及员工权限使用各自 DTO。草稿可以表达模板对象的字段、标题、defaultView、employeeAccess 子集。理由、临时 ID、未采纳项仅供预览。V1 不生成模板版本、流程、自动化、公海、仪表盘或目标。[模板结构](../../../apps/api/src/modules/business-templates/business-template.schema.ts)
- 支持 TEXT、TEXTAREA、PHONE、EMAIL、NUMBER、MONEY、DATE、DATETIME、SINGLE_SELECT、MULTI_SELECT、MEMBER、BOOLEAN。简单校验直接走手动策略，如数字的 min/max/scale；不接受自由脚本或任意配置 JSON。标题必须存在、必填，使用手动支持的 TEXT、PHONE、EMAIL 或 SINGLE_SELECT。

## 编码、冲突、内置能力

- 名称去首尾空白。重名比较使用 Unicode NFKC、大小写折叠及空白规范化，保留原展示名。在租户内检查草稿、已发布与已归档对象，以及本蓝图的其他表。补字段同时检查目标表全部字段（含停用字段）和本次建议。冲突标到对应行，管理员改名或删除后才能确认。
- 表编码满足现有小写字母、数字与单连字符规则；字段键使用小写字母、数字与单下划线；都以字母开头，长度按 DTO。服务端可采用符合规则的英文建议作候选。无可用 ASCII 名时以 `obj-` 或 `field_` 加稳定临时 ID 的短码生成，复验显示最终编码。相同标签先报重名；不同名编码碰撞可生成合法后缀并展示。确认时若展示过的编码被占用，返回冲突要求重新预览。数据库租户编码唯一约束作最后防线。
- 选项去空白，按规范化标签去重，保留顺序并提示被合并项；选项键由服务端分配。初始字段每个选项列表最多 100 项。视图列必须引用本表仍存在的字段。删除标题、删掉视图引用、修改类型引起选项或校验失效，均提示到对应行；管理员完成修正后才能写入。
- 内置能力用有限的语义分类与已知系统键、明确别名核对，包括归属、公海、编号、创建和更新时间、跟进与下次跟进、沟通纪要、附件、记录关联。预览逐项说明可去哪里使用。用实体职责区分「跟进记录表」与独立业务「设备维修工单」，区分「负责人」与「技术顾问」、「下次跟进日期」与「合同到期日」。近义冲突给出候选已有项及理由，请管理员消歧，避免宽泛子串误删业务字段。
- 公式、附件字段、关联字段进未采纳清单。例如自动毛利可建议管理员另行选择手工金额，关联客户可用记录关联，附件可用记录附件区。未经选择不生成替代字段。第七个明确实体在预览中点名，提示选六张或分批；不截断后直接创建。
- 员工动作逐项与手动默认值比较，范围按 NONE ≤ OWN ≤ ALL，字段权限按实际允许的操作集合比较。任何超出基线的建议留作未采纳意图，生成预览明确展示实际权限；确认请求若自带越权配置则拒绝整批。补充字段显式为 HIDDEN，原表权限、现有字段和当前发布快照保持原值。

## 预览、追问与调整

拟设管理员路由前缀 `/workspaces/:tenantCode/ai/table-builder`。所有入口先重解租户成员并复用建表管理员判定，随后才调用模型或读取元数据。预览和确认都使用严格 DTO 白名单。

| 操作 | 输入 | 输出与副作用 |
| --- | --- | --- |
| POST preview | 描述、模式、可选目标对象、已答问题 | `question` 或 `blueprint`；返回规范化编码、权限、未采纳项及 issues |
| POST validate | 当前蓝图；补字段时带对象及草稿版本 | 用服务端最新元数据重验，返回预览结果；不调用模型 |
| POST refine | 当前蓝图、选中表 ID、修改说明 | 返回该表的候选修改和差异；其他表不变 |
| POST confirm | 模式、管理员最终选择、已预览编码、补字段的 expectedVersion | 同一事务创建草稿或追加字段，返回对象 ID、版本及下一步链接；无发布副作用 |

**存储决定。** V1 把描述、选项答案及蓝图存在当前页面内存，切换租户、退出或关闭页面即清除。网络或 provider 失败保留输入和最后一个有效预览。刷新恢复后置；页面有未确认编辑时提示。服务端每次从当前身份解析上下文并校验整份输入；前端传来的角色、表摘要或临时 ID 均不能授权。没有蓝图临时表、数据库写入或跨成员可复用的预览凭证。

**最多两个问题。** 行业、主要管理实体采用固定问题键；服务端构造可选项和「其他」文本框，复用 QuestionCard 的选项呈现与 PreviewChoices。生成接口收到形如 `{key, choiceId, otherText?}` 的回答，校验键、选项、长度、去重与回答次序，再决定下一个问题。需要从上次生成的动态选项中选择时，不接受客户端自报选项；V1 仅提供服务端可重新构造的固定选项。每类最多问一次，两题后按现有信息列明假设。描述充分时直接预览。本流程无聊天会话和写入提议。

**编辑。** 左侧表列表带字段数和问题数，支持移除；右侧为表名、说明、标题、默认列、员工权限、字段行（标签／类型／必填／选项／理由）。底部固定「已内置／未采纳」「整组重新生成」「确认创建 N 张草稿」。补字段模式左侧锁定目标表，原字段只读。空租户首屏在「创建第一张业务表」旁展示「用 AI 描述生成」，常规入口在新建下拉，设计器仅挂载按钮。
- 本地输入立即显示，编辑后调用 validate，每次带编辑序号，只接收最新响应；有待验变更或阻塞项时禁用确认。「整组重新生成」覆盖前提示。
- 「按说明调整」只允许修改目标蓝图表；按稳定 ID 比较编辑前后的属性。新增 ID 是新增，原 ID 属性变更是修改，原 ID 缺失是删除。重复、跨表或未知的既有 ID 拒绝；新项由服务端分配 ID。展示旧值、新值、删除项后由管理员采用。确认保存的是最后一次编辑与核对的版本。
- 补字段重新读取指定表，最多 10 个，仅允许新增。模型或客户端夹带重命名、删除、权限提升或已有键修改，整次拒绝。已发布表追加到草稿，发布前记录页面仍用旧快照。

## 确认事务与单独发布

1. 手动建表、更新默认视图和权限目前会各自打开 `repository.withTenant`。将已有动作中「在 ObjectsStore 上做事」的部分提取为事务内方法，手动入口继续委托同一方法。批量确认仅开一次租户事务，锁内重读配置、管理员权限和占用情况。对并发建表与改表名共用配置锁，避免检查同名后被另一个写入抢占。
2. 在模型调用完成、管理员确认后才开始写事务。每表执行建草稿、追加 MEMBER、写说明、设置默认视图和员工权限。用上一步实际返回版本执行下一步，最终重验完整草稿。每个动作原有审计与业务写入使用同一事务；第三表失败，前两表、字段、视图、权限与审计一起回滚。确认按钮防重复；服务端的锁、重名和版本检查保证同一请求重放不会再建一套。补字段同样在单事务内锁对象并核对 expectedVersion。
3. 成功页持有本批提交返回的对象 ID。进入整组发布页后，以当前租户重新读取这些草稿，展示发布分析和预计版本。模板来源继续校验完整模板候选集；显式组来源只接受唯一且属于本租户、可发布的草稿 ID。抽取并共享既有组发布核心，按固定顺序加锁、核对对象与公海配置版本、检查依赖、整批分析、调用同一 commitPublication。版本过期、权限不足或一个对象阻塞，整组不发布。没有模板依赖，也不伪造模板版本。管理员可先打开现有权限编辑器配置读写与字段权限，再回来重新分析。刷新丢失批次选择时仍可从管理页逐表发布。

## 验证和交付门槛

按契约与校验 → 事务创建 → provider → 预览页与补字段 → 评测的顺序先写测试。检查 OpenAPI 漂移；每批运行全仓类型检查、相关单测、HTTP E2E 及数据库集成。权限和原子性用真实 PostgreSQL/RLS、两租户及并发确认验证。
- 服务端回归覆盖员工所有端点 403、跨租户对象、归档名称与编码、MEMBER 初始限制、系统能力同义项、合法业务字段误删、越权配置、两次同时确认、补字段版本冲突、第三张失败后零残留、发布前员工看不到变化以及现有模板整组发布回归。
- 评测样本形如 `{id, industry, description, existingObjects, answers, mustCover:[{entity, fields:[{meaning,type,options?}]}], mustOmit, permissionCeiling}`。开发集 20 条，独立作者在试跑前冻结留出集 10 条，分开计分。覆盖设备租赁、教培、装修、外贸、软件、医美、物业、招聘；交叉覆盖英文、单表、超限、模糊、冲突、注入、平台内置和不支持类型。
- 分别记录原始模型建议、服务端拒绝原因、最终可确认配置和未采纳项（仅脱敏样本）。对可创建配置按同一业务校验器计合法率，必须 100%；另报弃答、阻塞与核心实体覆盖，防止靠全部拒绝得满分。记录关键类型和选项命中、未采纳覆盖。最终预览中重复内置项或宽于基线的权限出现一次即阻断；对伪造确认额外核验零写入。方案划分、字段实用性、选项贴合度按三项 0–2 分抽查，并标明真人或模型评分。默认 fake，只在本机显式环境配置下跑真实模型。
- 浏览器以刘洋、1440×900 和 fake 执行九个场景：设备租赁方案；删除和单表调整后确认三张并手动授权发布、赵晨建记录；模糊描述追问；毛利公式与关联说明；已有表重名；第三张注入失败并查库；已有客户表补字段；员工无入口且 API 拒绝、权限注入失效；模型不可用后保留原文并回到手动建表。主流程截图及结果放入当日 `docs/audits/.../ai-table-builder/`。

后续可将已验证的结构子集导出到行业模板；关联、公式需先有相应字段契约；自动化、流程、仪表盘等需各自的权限与确认设计。示例数据、AI 文件导入、用量配额和已有字段的改删不进入本版。本规格尚未实施，模型得分、浏览器场景和运行测试均待实施阶段验证。
